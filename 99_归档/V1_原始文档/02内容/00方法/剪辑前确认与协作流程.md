# 剪辑前确认与协作流程

> 状态：2026-08-11 建立。用于真人口播、电脑录屏、论文证据和 HyperFrames 动效混合的视频。
>
> 目的：把必须在开剪前确认的事项、助手不能擅自决定的边界、审片方式和工具取舍固定下来。单条视频的具体选择仍写入该条视频的制作文件，不把“建议值”误写成已经确认的事实。
>
> 成片导出后的文件保留、两轮清理和正式收尾，见《单条视频收尾与归档规则.md》；不要把“导出成功”误当成可以立即删除可编辑工程。
>
> 成片准备上传前，必须再执行《作品发布前检查与外部素材转载规则.md》；含外部视频、翻译字幕、官方宣传片或 AI 生成素材时，不能只检查画幅和字幕。

## 一、当前结论

第 1 条采用 **HyperFrames 主合成 + 必要时再进人工剪辑软件微调** 的协作方式。助手可以直接完成素材盘点、粗剪建议、16:9 横屏合成、真人小窗复用、论文证据镜头、动态图卡、字幕、转场、音效和 MP4 渲染；不要求用户在助手工作时一直打开剪映配合操作。

当前不把“自动删停顿”“一键爆款包装”或“直接生成剪映草稿”当作正式主流程。它们可以做分析或小样，但不能未经审看直接决定最终剪点。

原因：本项目的节奏依赖本人语气、自然停顿、口播重音与证据画面的同步；按音量阈值自动删静音很容易误删思考停顿、句尾呼吸和情绪留白。第 1 条又已经按 18 个语义片段录好，自动场景检测的收益很低。

## 二、开剪前的硬确认项

正式改变素材时间线或生成整条动效前，必须把下表分为“已确认”和“待确认”。助手可以给推荐值和理由，但不能把推荐值直接当作用户答案。

| 类别 | 必须确认的内容 | 第 1 条当前状态 |
|---|---|---|
| 发布端 | 首发平台、是否同时做其他平台版本 | 抖音首发已明确；其他平台版本未确认 |
| 画布 | 横竖比例、最终分辨率 | 保持原片 16:9 横屏已确认；1920×1080 与原片一致 |
| 帧率 | 30fps 或 60fps | 18 段原片均为 60fps；建议保留 60fps，待确认 |
| 时长 | 目标区间和可接受上限 | 原片含前后余量共 4:32.82；建议粗剪先以约 3:45—4:10 为目标，待确认 |
| 主画面 | 电脑录屏、真实证据、生成画面的占比 | 电脑画面为主，论文与纯动效按口播补位，已确认 |
| 真人小窗 | 是否全程保留、位置、尺寸、圆角和阴影 | 全程保留已确认；16:9 中保持与原片一致，完整替换主画面时由代表性样片复刻 |
| 视觉风格 | 配色、字体、卡片材质、科技感强度、动效强度 | 新增文字简约、克制、易读已确认；避免花哨“AI 模板感”，具体字体与强调色待样片确认 |
| 字幕层级 | 普通口播字幕、T1 动态重音、证据翻译条分别怎么用 | 三者分层原则已确认；具体字体、字号和位置待样片确认 |
| 转场 | 硬切、J-cut、L-cut、遮罩/推拉等使用密度 | 以声音连续和语义承接为主已形成方向；具体样式待样片验证 |
| 音频 | 人声清理强度、BGM 有无、SFX 密度、最终响度 | 人声优先、点音克制已确认；第 1 条不铺持续 BGM，后续逐条判断，不把 BGM 当默认轨 |
| 可编辑交付 | 最终 MP4 之外是否必须交付剪映/CapCut 可编辑草稿 | HyperFrames 工程与分层素材可交付；剪映草稿方案待独立小样验证 |
| 不可动项 | 哪些口播、段落顺序、证据和画面已锁定 | 以最终 Word、18 段原片和现行分镜约定为准；结构性改动必须先说明 |

### 第 1 条素材技术事实

- 18 段原片均为 H.264、1920×1080、60fps；音频为 AAC、48kHz、双声道。
- 总时长 272.817 秒（4:32.82），总大小约 338MB。
- 以本机 M5、24GB 内存和当前素材量，默认不先制作代理文件；只有实际预览卡顿时才增加代理，不把它当固定步骤。
- 最终保持原片 16:9，不做竖屏自动裁切；每个语义段仍要复核电脑重点区域、真人小窗、字幕和动效是否同时可读。

### 口播自然度试录门（从第2条起执行）

- 助手必须在正式长录开始前主动提醒，不能等用户整条录完后才检查播报感。
- 使用本期真实稿件中同时含有情绪、长句或数据的一段，先录20—30秒；至少比较一次逐字读稿和一次只看关键词的自然复述。
- 判断标准不是“字正腔圆”，而是像对一个具体的人说话：有自然的轻重、快慢和停顿，句句不等重，结尾不刻意收成新闻腔。
- 如果测试仍明显像播报，先调整断句、提词器呈现、关键词提示或表达状态；只有用户确认“自然度可以接受”，才开始整条录制。
- 正式录制通过后再锁定音频并设计动效，避免口播问题拖到剪辑阶段才发现，导致重录与动画卡点全部返工。

## 三、助手必须遵守的剪辑约束

1. **原片只读。** 不覆盖、不改名、不在原片目录里生成中间文件。所有工程、缓存、预览和导出进入独立剪辑目录。
2. **先粗剪，后动效。** 先确认叙事顺序、停顿、重复、口误和段落长度；结构未锁定前不批量制作精细动效，避免后续整段返工。
3. **自动检测只给建议。** 可以用音量、波形、转写或停顿检测标出候选剪点，但不能未经人工听看就自动删除。
4. **不擅自加速整段人声。** 若某段显慢，先删无意义空白或换画面节奏；整体倍速、变调、强降噪或 AI 人声增强必须先做对比样片。
5. **口播是时间主轨。** 图标、卡片、论文高亮、翻译、数字和音效全部绑定实际录音中的关键词落点，不按文稿字数估时。
6. **真实证据不生成。** 论文、报告、数据、网页和产品界面使用真实素材；生成层只做放大、高亮、翻译、批注、构图和解释，不伪造正文、数字或软件结果。
7. **普通字幕与动态重音分层。** 普通字幕负责准确理解，T1/T2 只负责少量语义重音；一句最多一个主视觉重音，不能把每个词都做成动画。
8. **新增文字保持简约。** 以清晰字号、字重、留白和少量强调色为主，不使用炫光、复杂渐变、连续弹跳、过量粒子或花哨的“AI 模板感”。
9. **安全区不是一次性模板。** 制作时保留保守安全边距，正式导出前再用当前版本抖音的上传预览核对右侧按钮、底部标题/进度、顶部状态区和不同页面裁切。
10. **重要图层分轨并可关闭。** 主画面、真人小窗、普通字幕、动态重音、证据标注、SFX、BGM 分开管理；结构确认后逐层锁定，避免修改字幕时误动小窗或音频。
11. **一次只解决一个审片层级。** 粗剪阶段不讨论阴影像素，风格样片阶段不重新改整篇口播，成片阶段不因一个点音重做已确认结构。
12. **每次改动可追溯。** 预览使用 `R1_粗剪`、`R2_风格样片`、`V1_完整审片`、`V2_修改审片` 等版本名；不覆盖上一版。
13. **发布前双重验收。** 电脑看完整画质和同步，手机按抖音实际播放方式看字号、遮挡、音量和注意力焦点；再进入抖音上传预览做最终 UI 安全区检查。

### BGM 采用判断（逐条决定）

- BGM 不是短视频的默认必选项。每条视频都要先判断它是否真的提供了情绪、节奏或段落结构，不能因为“短视频都该有音乐”而机械铺底。
- 论文、数据、软件操作和连续解释占比较高时，优先保留干净人声和必要留白；若口播本身偏播报，持续 BGM 可能进一步放大新闻腔，应优先不加。
- 情绪叙事、轻量展示、蒙太奇或节奏明显的教程，可以做低存在感 BGM 小样，再与纯人声版比较后决定。
- 不采用 BGM 不等于完全无声音设计：仍可在转场、图标落点、数字结论和章节切换处使用少量 T2 点音，但不能连续铺满。
- 一旦采用 BGM，必须与口播建立动态让位关系，最终以手机外放时每句话仍能一次听清为验收标准。

## 四、推荐的五道协作关卡

### 1. 素材盘点与粗剪地图

- 核对文件、时长、帧率、音轨、顺序和缺失素材。
- 转写音频，标记口误、重复、长停顿、可做 J/L-cut 的交界处。
- 只输出“建议剪点与理由”，不先做复杂视觉。

### 2. R1 粗剪审片：先锁内容和节奏

- 只保留原片 16:9 横屏构图、真人小窗和临时字幕。
- 用户主要判断：有没有播音腔被剪得更重、停顿是否自然、哪段拖、哪句不该删、顺序是否顺。
- R1 通过后形成结构锁；后续如需结构性返工，必须先说明会牵连哪些动效和字幕。

### 3. R2 代表性风格样片：再锁视觉语言

选择 10—20 秒、同时包含电脑录屏、真人小窗、一个动态图卡或论文证据、普通字幕和一个点音的真实片段。一次确认：

- 16:9 构图和小窗复刻；
- 配色、字体、卡片质感；
- 动效强度、进入速度和稳定停留时间；
- 普通字幕与动态重音的层级；
- 人声清理、SFX 与 BGM 的相对音量。

样片未确认，不把同一风格批量复制到整条视频。

### 4. V1 完整审片：带时间码收意见

- 完整生成后先导出审片版，临时叠加不遮内容的时间码和版本号。
- 反馈统一用：`时间码/时间段 + 保留/删除/修改 + 具体原因或目标`。
- 例如：`01:18.4—01:21.0，修改：数据卡太抢人，保留数字但减弱入场。`
- 一轮内尽量集中反馈，避免不同消息互相覆盖；每条反馈标记“已改 / 保留原版 / 待决定”。

### 5. 最终导出与发布预览

- 移除审片时间码和临时标记，输出平台母版。
- 保留 HyperFrames 工程、字幕文件、素材清单和来源记录；平台版本从母版复制，不直接在唯一工程上破坏性修改。
- 上传抖音但不立即发布，先检查封面裁切、字幕遮挡、音量、清晰度和是否出现意外水印。

## 五、建议的分轨结构

```text
V7  来源/年份/必要合规标注
V6  T1 动态重音与短点音对应标记
V5  普通口播字幕
V4  图标、卡片、流程、数据与批注
V3  真人小窗（固定位置、圆角、描边、重建阴影）
V2  论文、网站、简历系统等替换主画面
V1  Recordly 原片安全底轨

A3  BGM（若采用）
A2  SFX 点音
A1  口播主音轨
```

## 六、工具与插件判断

| 工具 | 能解决什么 | 当前判断 | 约束 |
|---|---|---|---|
| HyperFrames + general-video | 现有素材重排、16:9 合成、真人小窗、论文镜头、动态图卡、字幕、音效与完整渲染 | 当前主流程 | 先确认 brief 和样片；动画必须可定位、可重复渲染 |
| HyperFrames 动画/媒体技能 | GSAP 动效、字幕、转写、背景移除、音效和素材管理 | 按需调用 | 不是“每个技能都用”；只在具体镜头需要时触发 |
| Auto-Editor | 依据音量/运动标记静音和候选剪点，可导出部分 NLE 时间线 | 当前只借鉴 | 只做候选检测；不允许直接自动删完并当成粗剪终稿 |
| Subtitle Edit 5 | 本地转写、波形对齐、字幕拆分合并、拼写与时间修正 | 到点复核 | 若 HyperFrames/剪映字幕校对成为瓶颈再安装；机器转写必须人工校对专有名词 |
| cutcli | 从命令或 JSON 生成可在 CapCut/剪映继续编辑的草稿 | 到点复核 | 先在隔离草稿和非敏感 10 秒样片中验证；不默认启用云渲染，不上传原片；第三方 CLI 本体与开源 cookbook 要分开审查 |
| pyJianYingDraft | Python 生成剪映草稿、模板替换 | 当前不采用 | 官方说明 macOS 不能自动导出，生成草稿仍需 Windows 版剪映导出，不匹配本机工作流 |
| PySceneDetect | 自动找硬切和淡入淡出 | 当前不采用 | 第 1 条已拆成 18 个语义片段，收益很低 |
| LosslessCut | 无重编码快速裁切、合并、拆轨 | 备用工具 | 适合超大原片先清理；当前 338MB 素材不构成阻塞，也不能完成复杂合成 |
| OpenTimelineIO | 在不同专业剪辑软件间交换剪辑时间线 | 到点复核 | 只有确定要交接 Premiere/Resolve/FCP 时才有价值 |
| Frame.io / CapCut Share for review | 按帧或时间段评论、版本对比和审片 | 到点复核 | 当前先用带时间码审片版；反馈轮次多到聊天难以管理时再接入外部服务 |

### 关于“要不要再装插件”

当前不建议为了剪辑再安装通用 Codex 插件。Codex 官方把 **Skill** 定位为可重复流程的说明、脚本和参考，把 **Plugin** 定位为可安装的能力包，常用于连接外部服务。第 1 条的主要阻塞是剪辑判断和样片验收，不是缺少 Gmail、Canva、Figma、GitHub 等外部连接。

因此现在更应该先跑通一条视频，并把稳定下来的“剪前确认—粗剪—样片—审片—导出”固化为本项目 skill；当确实要连接 Figma、Canva、云端审片或剪映草稿服务时，再安装对应插件或连接器。
