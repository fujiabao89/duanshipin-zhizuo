# 脚本方法

## 共创分工

用户可以只提供零散原话、观点、必留片段、参考和方向，不需要先写完整稿。助手负责核验专业内容、补全未指定部分、连接成完整候选，并在交付中区分原话、补写和待核实内容。

### 两类输入

- 原话及必留内容：用户明确指定句子、力度、观点、位置或镜头时，默认锁定，不因更正式、更克制或助手审美而删除。
- 方向委托：用户只说明“可以讲什么”时，助手保留意图，主动查证、选择信息、补写口播和衔接。

真正影响方向但含糊的地方再定点询问，不把整篇写稿任务退回用户。

## 推荐结构

脚本围绕一个真正命题推进，可根据题材调整：

```text
共同语境或可见结果
→ 具体问题
→ 本人判断
→ 真实例子或操作
→ 原因与证据
→ 局限或适用范围
→ 从前文自然长出的结论
```

丰满不等于堆功能。只保留能推进本条命题的例子、步骤和解释。

## 论点与证据

专业感主要来自“观点 + 证据画面 + 真实演示”，不要求把口播写成论文。遇到有吸引力但证据不足的表达，按以下顺序处理：识别吸引目的 → 主动找证据 → 收窄范围但保留利益点 → 标明个人观点 → 确实误导时才建议删除。

不编造体验、测试结果、功能、接口、市场份额或完成时间。事实问题单独说明证据和最小改法，不能借核验顺带改写全部本人表达。

## 观众行动检查

- 谁为什么愿意继续看？
- 本条最希望观众自然做什么？
- 是否给了这个动作真实理由？
- 有没有值得以后回来照着做的清单、步骤或方法？
- 谁会把它转给谁，转发的用途是什么？

每条不机械追求所有指标，也不强塞点赞、评论、收藏、关注四连。

## 版本与交付

- 脚本默认交付 Word，口播和画面/声音备注清楚分列；Markdown 不替代正式阅读稿。
- 制作中版本号放在文件名前并递增，不因格式变化重新编号。
- 用户确认可拍摄后，核对最后保存内容，收口为案例目录中的 `最终脚本.docx`；旧版本进入可恢复归档。
- 项目卡只保存状态与入口，不塞入整篇脚本。

## 确认门

用户决定最终增加、删除、保留和口吻。只有用户明确“脚本可以开始拍摄”，才进入拍摄；音效、变声、转场和视觉在脚本阶段只能作为候选，未看实际样片不能升级为长期风格。
