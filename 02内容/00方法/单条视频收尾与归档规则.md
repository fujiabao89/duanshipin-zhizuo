# 单条视频收尾与归档规则

> 建立时间：2026-08-23。  
> 来源：第1条视频从脚本、Recordly录制、HyperFrames剪辑到最终导出的完整实践。  
> 目的：让以后每条视频结束时既不堆积大量缓存，也不因过早删除而失去返修能力。
>
> **强制执行：** 每条视频完成后都必须走本流程。助手应主动发起，不等待用户再次提醒；未完成核验、清理和项目简报更新，不算正式结束。

## 一、什么时候才算正式结束

2026-09-06补充：以下条件用于“制作资产收尾”。项目现在另设“发布完成”和“本轮复盘完成”，见《短视频五阶段协作总规则.md》；制作完成不能自动记为已经发布、已经复盘。等待数据时可以按既有约定清理制作缓存，保留轻量发布与复盘记录。

一条视频同时满足以下条件，才进入最终归档：

1. 最终MP4已经导出，并从头到尾完成一次画面与声音检查；
2. 封面已经确认，并核对平台实际裁切；
3. 最终脚本、成片、封面和录制原片都能从固定路径找到；
4. 关键文件完成大小、时长或哈希核验；
5. 用户明确确认“这一条正式结束”。

只完成视频但封面尚未确认，不算彻底结束。此时可以瘦身，但不能删除当前可编辑主工程。

脚本版本收口不再等到本阶段。用户确认脚本可以拍摄时，就按《短视频五阶段协作总规则.md》只保留《第N条视频脚本.docx》，旧脚本进入可恢复废纸篓。

## 二、采用三次阶段清理

### 第一轮：脚本锁定后

- 核对用户最后保存的Word内容；
- 《01脚本/》只保留《第N条视频脚本.docx》；
- 旧脚本版本移入带日期的可恢复废纸篓；
- 更新当期《制作状态.md》后进入拍摄。

### 第二轮：成片确认后、封面确认前

必须保留：

- 所有录制原片；
- 最终MP4；
- 当前最终脚本；
- 全部封面候选与封面规范；
- 当前可编辑的HyperFrames主工程、工程媒体工作副本和素材清单；
- 论文、报告、真实网页和其他证据来源；
- 属于真实项目资产的网站或程序源码。

可以移入废纸篓：

- QA截图、联系表、测试渲染、缩略图和波形缓存；
- 已完成校对后的临时转写、剪点JSON/TSV和一次性辅助脚本；
- 旧工程备份、试验性HTML和已经退出使用的中间稿；
- 可以由锁文件重新安装的 `node_modules` 等依赖目录。

### 第三轮：封面确认并正式结束后

默认长期保留：

- `录制原片/`；
- `01脚本/第N条视频脚本.docx`，只保留这一份且不带 `vN_`；
- 最终成片；
- 最终封面；
- 需要承担事实、授权或来源证明的论文、数据与素材记录；
- 有真实复用价值的网站、程序或其他项目源码；
- 一份最终文件清单或哈希记录。

新增长期保留：本条《发布与复盘.md》，其中包括实际发布文案、标签、发布链接／时间、数据口径、必要的文案变更记录和有价值的复盘结论。待发布或待复盘的字段保留真实状态，不补造；相关记录不按制作中间文件删除。

是否继续保留整个HyperFrames可编辑工程，由用户在正式结束时决定。若未来可能改字幕、裁平台版本或修正事实，保留工程；若确认只留发布成果，可再移除媒体工作副本、工程缓存和合成文件。

所有删除先进入一个带日期的废纸篓文件夹。用户查看清单并确认后，才清空废纸篓；清空前不会真正释放磁盘空间。

## 三、最终命名

```text
第N条：主题/
├── 01脚本/第N条视频脚本.docx
├── 录制原片/
├── 发布与复盘.md
└── 论文、参考视频、网站或其他确需保留的真实资产

桌面/剪辑/第N条：主题/第N条视频.mp4
桌面/封面/第N条：主题.png
```

2026-09-14起，短视频制作中的单条目录、剪辑子目录和最终封面使用同一基准名《第N条：主题》。所有正式成片统一放在桌面 `/Users/bohan/Desktop/剪辑/第N条：主题/`；`02内容/` 不长期保留正式MP4副本。最终封面直接集中保存到桌面 `/Users/bohan/Desktop/封面/`，不在短视频制作目录另设长期正式封面副本。

修订版经用户确认成为当前正式版后，正式文件仍命名为 `第N条视频.mp4`。如旧版已经发布或有回退价值，则在同一目录改名为 `第N条视频_原发布版.mp4`；普通预览、试听和测试渲染按过程文件进入可恢复废纸篓。

制作过程中可以使用 `vN_`、`R1`、`R2`、`V1` 等版本号；正式归档文件不再携带制作过程版本号。

## 四、第1条积累的制作规则

### 录制与口播

- 正式长录前先录20—30秒自然度测试，同时比较“逐字读稿”和“只看关键词复述”。目标是像对一个具体的人说话，不是字正腔圆。
- Recordly同源录屏、人物小窗和声音能减少音画不同步；原片始终只读，剪辑只使用工作副本。
- 画幅、帧率、人物小窗大小、字幕风格和动效强度在正式录制前确认，避免剪到一半重新定义画布。
- 用户边录边确认的新想法必须当天写回当前脚本，聊天记录不能成为唯一依据。

### 脚本与表达

- 用户手稿是修改底稿，不是自由重写的需求说明。本人原话、情绪和段落顺序默认锁定，只局部顺句；专业解释只在明确委托处补写。
- 口播自然度问题不能全靠剪辑掩盖。剪辑可以改善停顿和观看节奏，但无法把新闻播报腔彻底变成聊天感。
- 第一条用了很久的核心教训之一，是脚本、录制和剪辑不能完全串行到最后才验收；下一条要把自然度样片和视觉样片提前。

### 剪辑与动效

- 口播音频是时间主轨。卡片、图标、论文高亮、翻译、字幕和音效都必须落在真实重音上。
- 原画面无法表达口播含义时，动效负责“解释”，不是把口播原句再放进一张白色卡片。网站、软件、手脚、拆任务等概念应优先做成直观图形或真实界面对比。
- 论文画面使用真实报告作为背景，再叠加推近、高亮、翻译和批注；证据层随镜头缩回或切走时必须同步消失。
- 真人小窗、主画面和字幕分轨。主视觉按完整画布正中构图，不为了躲小窗而整体偏心；字幕保持视觉居中，同时避开人物与平台UI。
- 不是所有动效都用同一字号、同一白底和同一尺寸。重点词可以放大，辅助信息应减弱；能透明呈现就不强加割裂的白卡底。
- 转场优先用声音桥、语义承接和新画面自身的进入动作。J-cut/L-cut、轻推近和压暗可以缓解硬切，但同一条只保留2—3种稳定语言。
- BGM逐条判断，不是默认必选项。论文、数据和连续解释较多时，干净人声和少量点音通常更合适。

### 审片与提速

- 先做10—20秒代表性样片锁定字体、字幕、人物小窗、转场和动效强度，再批量制作整片。
- 样片通过后采用“整片批量制作 → 用户一次集中带时间码反馈 → 一轮统一修改”，不再逐镜头等一次确认才继续。
- 反馈区分客观错误和审美选择：黄条残留、黑边、字幕偏心、画面卡死属于必须修；颜色、字号和动效强弱属于集中对接的审美项。
- 每次完整修改后，助手必须像观众一样从头到尾检查，而不能只检查改动的时间点。

### HyperFrames与最终质检

- Studio是本地预览服务，不是成片。黑屏、卡住或无声可能来自预览进程、重复标签页或浏览器媒体解码资源，不应未经核对就改坏正确的composition。
- 同一工程只保留一个Studio标签页。交付预览前必须确认本地服务真正可访问，并实播至少3秒确认画面与声音时钟都在前进。
- 已确认工程固定CLI版本，避免临近导出时自动升级导致画面变化；升级只能在单独副本中检查。
- 最终MP4必须单独验收：核对分辨率、帧率、时长和音轨；从头到尾看一遍；重点复核画面切换点、字幕与高亮退场、人物小窗边缘，以及曾出现噪音或卡顿的时间段。

## 五、每条视频结束时的交接清单

- [ ] 最终MP4可播放，画面与声音完整
- [ ] 封面已确认并通过平台裁切预览
- [ ] 最终脚本已去掉版本号，旧版本已移入废纸篓
- [ ] 原片数量、大小或哈希未变化
- [ ] 证据来源和授权记录已保留
- [ ] 发布文案、标签与复盘记录已保留；制作、发布、复盘状态分别标注
- [ ] 缓存、测试渲染、转写和辅助脚本已移入废纸篓
- [ ] 用户已看过“保留/移走”清单
- [ ] 用户已决定是否保留可编辑工程
- [ ] 用户确认后再清空废纸篓
